# ESM Viewer product website

An English-language, static product page for GitHub Pages. It explains the shipped Viewer application's inspection, verification, compliance review and report features, with supported downloads, privacy, installation details and practical questions. The opening hero and screenshot gallery show the actual application rendered with synthetic test records; a contained diagram illustrates the offline workflow. The page is not a browser version of the desktop application. Planned Cases functionality is not advertised as available.

## Preview locally

Open `docs/site/index.html` directly for a source preview. It references the existing shared foundation styles in the repository and includes the logo in `assets/icon.png`, so it works without first building the site. Run `pnpm site:build`, then open `dist/site/index.html` to preview the self-contained GitHub Pages artifact. To preview that artifact over HTTP, run `python3 -m http.server 8080 --directory dist/site` and visit `http://localhost:8080`.

The build copies the page's authored assets and the existing `src/ui/styles` foundation, tokens, handbook and preferences styles into a self-contained `dist/site` artifact, then refreshes its icon from the native app. It rewrites the source HTML's foundation stylesheet URL to the staged `assets/design` path; repository source paths are not published. Shared styles have one source of truth. The source-preview logo is the same application icon; refresh `assets/icon.png` when that brand asset changes. Product-page overrides use `assets/site-tokens.css`. No dependency installation, parser, desktop build, external font, analytics, external map or CDN is needed. The build needs an internet connection to resolve the latest published stable release through GitHub's API; an optional `GITHUB_TOKEN` authenticates that build-time request and is never included in the artifact. JavaScript only enhances narrow-screen navigation, including focus and destination alignment after closing the menu; the page and links remain usable without it.

The page uses relative asset paths so it works both from a local file and under `/esm-viewer/`. Its download area uses three platform columns with rounded, two-line download buttons: the platform action is primary, the package format is secondary, and a shared decorative download icon is aligned at the end. Windows MSI and Linux DEB/RPM alternatives appear underneath. Platform-specific installation and warning instructions use native disclosures underneath the package choices. Header and FAQ links make this help available before installation; support guidance excludes personal tachograph data.

`tools/releases/release-assets.ts` resolves production assets by filename suffix, excludes debug and unfinished assets, and validates release/asset URLs against the repository and tag. Drafts and prereleases are rejected. The build inserts direct installer links and the release tag into static HTML; no client API lookup, token exposure or OS detection is used. Missing formats are explicitly unavailable, not redirected to another package. Failed API requests, ambiguous matches, invalid metadata or releases without any matching installer fail the build, preserving the previous deployed site. Source previews explicitly identify their fallback links as GitHub Releases links. Changing the repository name or owner also requires updating build selectors, canonical/Open Graph URLs and GitHub links.

## Publish with GitHub Pages

The `.github/workflows/pages.yml` workflow builds and uploads only `dist/site`, then deploys it through the `github-pages` environment with `pages: write` and `id-token: write` permissions on the deploy job. It does not publish the repository, application sources, implementation documents or UX prototype. The website build does not need submodules or `pnpm install`.

1. In this repository's **Settings → Pages → Build and deployment → Source**, choose **GitHub Actions**.
2. Once the website change is reviewed and merged into `master`, the **Product Website** workflow runs on changes to the site or its shared assets and whenever a stable release is published. A release-triggered build uses the website source from `master`, not the release tag, so publishing a desktop release refreshes installer links automatically without rebuilding the desktop app. Draft releases and prereleases do not deploy. It can also be run manually from Actions, selecting `master`.
3. The expected default URL is `https://mbolaric.github.io/esm-viewer/`. The deployment run exposes its actual published URL.

A manual run from another branch can build an artifact, but deployment is restricted to `master` or a stable-release event using `master` source. Publishing a release is the release-selection gate; an additional website deployment approval can be configured through required reviewers on the `github-pages` environment. Fork owners need to update project URLs before publishing their own page. The setup follows GitHub's [custom Pages workflow documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

The coding-agent change only prepares the files and workflow. Enabling Pages, committing, pushing or running a deployment are separate repository-owner actions.

## Maintaining the page

`docs/implementation.md` is the current-state product reference. Update page copy when shipped behavior changes; keep incomplete-record and verification-scope qualifications, and distinguish desktop privacy from the publicly hosted website. Installer signing/notarization copy should change when the release policy changes. Never add real tachograph downloads or screenshots containing personal data.

The site is covered by repository formatting/lint checks, strict JavaScript checks, and local browser checks for links, asset isolation, keyboard navigation, no-JavaScript navigation, responsive layouts, zoom, reduced motion and WCAG accessibility. Run `pnpm site:build` after editing source files; generated output is ignored by Git.

### Screenshot provenance

`assets/images/activities.png`, `compliance.png` and `raw-data.png` are 1440 × 1050 captures of the unchanged production `apps/viewer/src/renderer/App.svelte`, including the shell and real feature components, rendered in a local Vite preview. The preview reused `src/viewer/feature/__tests__/viewer-document-harness.ts` and `viewer-test-context.ts` to supply synthetic normalized records through test ports. The synthetic raw tree includes the same three activity intervals as the domain fixture. No personal download, native file read, native parser or signature verification was used. The visible `synthetic-driver.ddd` filename is a fixture label, not a real uploaded file.

The Activities capture scrolls to the complete timeline and records table. The Compliance capture runs the production compliance evaluator on those records: its five-hour driving interval produces a calculated Article 7 finding. The Raw data capture opens the recorded Other work interval's source link and selects `/activities/1/start`, showing its exact synthetic UTC value. Inferred unknown periods and external-evidence qualifications remain visible. Signature status is honestly shown as **Not checked**. The opening hero uses Activities once; the gallery shows the different Compliance and Raw data views. The privacy diagram remains an illustration. Screenshots have descriptive alt text, visible synthetic-data captions and full-size image links; gallery images load lazily while the opening image has high fetch priority. Their originals are included in the Pages artifact.
